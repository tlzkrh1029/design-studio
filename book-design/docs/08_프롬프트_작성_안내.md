# 8. 프롬프트 작성 안내: 브리프+토큰과 XML 태그

1차 실험 뒤에 사용자는 두 가지를 물었습니다. Claude가 추천한 방식(짧은 마크다운 브리프와 디자인 토큰을 함께 쓰는 방식)으로 디자인을 맡기려면 프롬프트를 어떻게 써야 하는지, 그리고 XML 태그를 쓴다면 어떻게 써야 하는지였습니다. Claude는 두 방식의 구성과 예시 프롬프트로 답했고, 그 구성을 바탕으로 2차 실험의 명세 작성 지시를 만들었습니다.

이 문서는 그 답변의 원문이 아니라, 답변 내용과 2차 실험에서 쓴 구성, 실험에서 얻은 교훈을 저장소에 남기려고 다시 정리한 것입니다. 실제로 쓰인 명세는 아래 파일에서 볼 수 있습니다.

- 브리프+토큰: [`cover_design/experiment2/specs/night.md`](../cover_design/experiment2/specs/night.md)
- XML 태그: [`cover_design/experiment2/specs/night.xml`](../cover_design/experiment2/specs/night.xml)
- 비교용 YAML: [`cover_design/experiment/specs/night.yaml`](../cover_design/experiment/specs/night.yaml)
- 명세 작성자에게 준 지시문: [`agents/17`](../agents/17_night_brief_plus_tokens_spec.md), [`agents/18`](../agents/18_night_xml_tag_spec.md)

## 두 방식에 공통된 원칙

Anthropic의 프롬프트 작성 지침([Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices))에서 이번 작업과 관련 있는 내용은 다음과 같습니다.

1. **맥락과 이유를 줍니다.** "어두운 바탕"이라고만 쓰기보다 "표지만 빛나야 하므로 바탕은 거의 검게"처럼 이유를 함께 적으면, 지시에 없는 상황에서도 같은 방향으로 판단합니다.
2. **할 것을 말합니다.** "영문 라벨을 쓰지 마라"보다 "구역 이름은 한국어로 쓴다"처럼 할 일을 적습니다. 금지가 꼭 필요하면 이유와 대신 할 일을 붙입니다.
3. **구체적으로 씁니다.** 화면 폭, 첫 화면에 보여야 할 것, 데이터의 실제 값, 상태(빈 날, 값 없음, 검색 결과 없음)를 적습니다.
4. **긴 자료는 위에, 지시는 맨 아래에 둡니다.** 데이터와 참고 자료를 먼저 두고 요청을 마지막에 두면 결과가 좋아집니다.
5. **완료 기준과 점검을 요구합니다.** 만든 뒤 렌더링 결과를 직접 보고 기준을 하나씩 확인하게 합니다.
6. **동료에게 보여 준다고 생각합니다.** 맥락을 모르는 사람이 읽어도 그대로 만들 수 있는지 확인합니다.

## 방식 1: 마크다운 브리프 + 디자인 토큰

브리프로 의도를 정하고, 토큰으로 값을 정하는 방식입니다. 브리프에는 '왜'와 판단 기준을 쓰고, 색상값이나 픽셀 같은 값은 토큰에만 씁니다. 만드는 사람은 토큰 값을 그대로 쓰고, 브리프가 열어 둔 결정은 브리프의 목적과 우선순위에 따라 스스로 내립니다.

### 구성

| 부분 | 쓸 내용 |
| --- | --- |
| 목적 | 페이지가 무엇인지, 누가 여는지, 그 사람이 하는 일 |
| 분위기 | 형용사에 그치지 않고 색, 글자, 바탕, 움직임을 어떻게 다룰지 |
| 참고한 것 | 기존 화면에서 지킬 것. 만드는 사람이 화면을 볼 수 없다면 말로 설명합니다. |
| 고칠 점 | 기존 화면의 약점과 각각을 어떻게 고칠지 |
| 우선순위 | 눈이 읽어야 할 순서 |
| 상태별 규칙 | 브리핑 없는 날, 다음 호, 하루에 여러 번 낸 날, 값 없음, 검색 결과 없음 |
| 피할 것 | 항목마다 이유와 대신 할 것 |
| 맡기는 부분 | 만드는 사람이 자유롭게 정해도 되는 것 |
| 완료 기준 | 완성된 페이지가 통과해야 할 점검 항목 |
| 토큰 | CSS `:root { }` 하나. 이름은 색이 아닌 역할로 짓습니다(`--text-2`, `--line-ref`). |
| 요청 | 브리프는 판단의 기준이고 토큰은 그대로 쓸 값이라는 점, 새 값은 토큰에 더하고 보고하라는 점 |

### 예시

````markdown
# 디자인 브리프: 크립토 브리핑 서고 · 밤의 가판대

## 목적
- 매일 06:10에 발행되는 크립토 브리핑을 날짜별로 모아 두는 서고다. 주인 한 사람이 매일 연다.
- 하는 일: ① 오늘 호를 확인하고 브리핑을 연다 ② 지난 호 표지를 훑는다 ③ 국면(A~E) 흐름을 본다
  ④ 날짜나 낱말로 지난 호를 찾는다 ⑤ 지표 추이를 본다.

## 분위기
- 밤에 불 켜진 신문 가판대. 거의 검은 바탕에서 빛은 표지에만 떨어진다.
- 색: 유채색은 표지, 국면 색, 오늘의 강조색(--accent) 셋뿐이다. --accent는 최신 호 표지의 테두리 색이다.
- 글자: 한글은 Gothic A1, 날짜와 큰 숫자는 Oswald. 위계는 크기 단계보다 굵기와 명도로 세운다.
- 움직임: 처음 열 때 조명만 천천히 켜진다.

## 참고한 것
- 히어로: 왼쪽에 받침 위의 최신 호 표지, 오른쪽에 날짜, 헤드라인, 국면, 지표 세 칸, 버튼 둘.

## 고칠 점
- 날짜가 헤드라인보다 커서 첫눈이 갈린다 → 헤드라인을 가장 큰 글자로, 날짜는 한 단계 아래로.

## 우선순위
1. 오늘 표지 2. 헤드라인 3. 국면과 지표 4. 지난 표지 5. 목록과 검색

## 상태별 규칙
- 브리핑 없는 날(9/18, 9/19)은 빈 자리로 보이고, 다음 호(10/1 06:10)는 점선 자리로 둔다.

## 피할 것
- 영문 장식 라벨: 화면 문구는 한국어가 원칙이다 → 구역 이름을 한국어로 쓴다.

## 맡기는 부분
- 조명의 모양, 선반의 질감, 구역 사이 장식.

## 완료 기준
- 1440×900 첫 화면에 표지, 헤드라인, '브리핑 펼치기'가 모두 보인다.
- 가로 스크롤이 없고, 본문 글자의 명암비가 4.5 이상이다.

# 토큰
```css
:root{
  --bg:#0C0E12;          /* 페이지 바탕 */
  --text-1:#F2F0EC;      /* 본문과 헤드라인 */
  --text-2:#B4B9C1;      /* 보조 글 */
  --line-ref:#6B727C;    /* 기준선(+1.0%p, 0) */
  --accent:#F2B39F;      /* 최신 호 표지 테두리 색. 날마다 바뀜 */
  --fs-headline:44px;
  --cover-hero:440px;
  --gutter:64px;
}
```

# 요청
위 브리프와 토큰으로 페이지를 만들어 주세요. 판단의 기준은 브리프이고, 토큰은 그대로 쓸 값입니다.
새 값이 꼭 필요하면 토큰에 더하고, 마지막에 무엇을 왜 더했는지 알려 주세요.
````

## 방식 2: XML 태그

지시, 맥락, 데이터, 참고, 예시를 태그로 나눠 주는 방식입니다. 태그 이름을 일관되게 쓰고, 지시에서 태그 이름으로 내용을 가리키면 어느 부분이 무엇인지 헷갈리지 않습니다.

### 작성 요령

- 내용마다 태그 하나를 두고, 이름은 내용을 설명하게 짓습니다.
- 계층이 있으면 태그를 겹칩니다(예: `<references>` 안에 `<reference index="1" part="히어로">`).
- 긴 자료(`<context>`, `<data>`, `<references>`)를 위에 두고, `<instructions>`를 맨 끝에 둡니다.
- 지시에서는 "`<tokens>`에 있는 값만 쓴다"처럼 태그 이름으로 가리킵니다.
- 출력도 태그로 요청합니다. 만들기 전 계획은 `<plan>`, 만든 뒤 점검은 `<check>`에 쓰게 합니다.
- 프롬프트이지 엄격한 XML 문서가 아니므로, 태그 안에는 평범한 글, Markdown 목록, CSS를 그대로 써도 됩니다.

### 예시

```xml
<context>
매일 06:10에 발행되는 크립토 브리핑을 날짜별로 모아 두는 서고 페이지를 새로 설계한다.
주인 한 사람이 매일 열어 오늘 호를 확인하고, 지난 호를 훑고, 국면과 지표의 흐름을 본다.
이번 작업은 표지를 담는 페이지(배경, 테마, 배치)를 바꾸는 것이고, 표지 자체는 바꾸지 않는다.
</context>

<data>
- 호 31개(9/2~9/30), 브리핑이 없는 날 2일(9/18, 9/19), 하루에 여러 번 발행한 날 3일(9/3, 9/5, 9/24).
- 최신 호: 제31호, 2026-09-30, 국면 C(선별적), BTC.D 59.18%(전날 +0.01%p).
- 기준선: ΣSTABLECOIN.D 1개월 변화 +1.0%p, BTCUSD 1개월 변화 0.
</data>

<references>
  <reference index="1" part="히어로">왼쪽 받침 위에 최신 호 표지 420px, 오른쪽에 날짜, 헤드라인, 국면, 지표 세 칸.</reference>
  <reference index="2" part="가판대">선반 3줄 × 7장, 아래에 날짜와 국면 표식.</reference>
</references>

<brief>
## 목적
…
## 분위기
…
## 고칠 점
…
## 우선순위
…
## 상태별 규칙
…
## 피할 것
…
## 맡기는 부분
…
## 완료 기준
…
</brief>

<tokens>
:root{ --bg:#0C0E12; --text-1:#F2F0EC; --accent:#F2B39F; /* … */ }
</tokens>

<instructions>
1. <brief>와 <tokens>로 페이지를 만든다. <brief>는 판단의 기준이고, <tokens>의 값은 그대로 쓴다.
2. 새 값이 꼭 필요하면 <tokens>에 더하고 마지막에 이유와 함께 알린다.
3. 만들기 전에 10줄 이내의 계획을 <plan>에 쓴다.
4. 만든 뒤 렌더링 결과를 직접 보고, <brief>의 완료 기준을 하나씩 점검해 결과를 <check>에 쓴다.
</instructions>
```

## 어느 방식을 고를까: 실험에서 얻은 교훈

2차 실험의 블라인드 평가 결과(평균 순위)는 명세 없이 1.83, YAML 2.33, 브리프+토큰 3.50, JSON 3.67, XML 태그 3.67이었습니다([06](06_명세_형식_실험_2차.md)). 형식 사이에 일관된 승자가 없었으므로, 형식보다 다음 점이 결과를 더 크게 좌우했다고 봅니다.

1. **원래 화면을 직접 보게 합니다.** 가장 좋은 점수를 받은 조건은 원래 시안과 브리프를 직접 보고 바로 만든 경우였습니다. 명세를 거쳐 넘기면, 화면을 본 사람의 감각이 말로 옮겨지는 동안 일부 빠집니다. 만드는 사람에게 참고 화면을 함께 줄 수 있다면 주는 편이 낫습니다.
2. **'왜'를 남깁니다.** 값만 적힌 명세는 빠뜨림을 줄여도 완성도를 보장하지 못했습니다. 목적, 우선순위, 피할 것의 이유가 있어야 명세에 없는 결정도 같은 방향으로 내립니다.
3. **배치를 정확히 고정하고 싶다면 구조화된 명세가 낫습니다.** 사용자가 고른 YAML 결과처럼, 열 구성과 크기를 그대로 옮기려면 구역 순서와 수치를 빠짐없이 적은 명세가 다시 만들기 쉽습니다.
4. **렌더링하고 점검하게 합니다.** 모든 조건의 만드는 사람에게 렌더링 결과를 직접 보고 겹침, 잘림, 넘침을 고치게 했습니다. XML 태그 조건의 `<check>`처럼 점검 결과를 글로 남기게 하면 무엇을 확인했는지 알 수 있습니다.
5. **결과를 한 번만 보고 단정하지 않습니다.** 조건마다 표본이 하나였으므로, 같은 조건으로 두세 번 만들어 비교하면 형식의 효과와 우연을 더 잘 가를 수 있습니다.
